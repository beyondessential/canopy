Identity token claim shapes

Two ways to shape the sub of a Canopy-issued token, worked through the same example. Lifetimes and the issuer name are placeholders.

The example

Group
Example Site 3f2a9c4e-6b1d-4e8a-9f07-2c5d8e1b4a6f
Machine
example-prod-1 51c8a0f3-2e7d-4b96-8a1c-e4f09b6d7c23, rank production
Application
Tamanu central 8d41e7b2-0c39-4f5a-a6e1-97b3c2d0f845
Grants
The application is granted the Anthropic audience. The machine is granted nothing.

Canopy only issues a token when the subject holds a grant for that audience. Everything below is about what a relying party can do with a token once Canopy has issued one.

What the token says

Both options carry the same flat claims. They differ only in sub.

S1 · opaque sub

Application token

{
  "iss": "https://idp.canopy.bes.au",
  "sub": "application:8d41e7b2-0c39-4f5a-a6e1-97b3c2d0f845",
  "aud": "https://api.anthropic.com",
  "iat": 1792130400,
  "nbf": 1792130400,
  "exp": 1792130700,
  "jti": "0b7e5c1a-94f2-4d3e-b8a6-71c0e2f9d455",
  "canopy_group_id": "3f2a9c4e-6b1d-4e8a-9f07-2c5d8e1b4a6f",
  "canopy_group_name": "Example Site",
  "canopy_rank": "production",
  "canopy_machine_id": "51c8a0f3-2e7d-4b96-8a1c-e4f09b6d7c23",
  "canopy_application_id": "8d41e7b2-0c39-4f5a-a6e1-97b3c2d0f845",
  "canopy_application_type": "tamanu-central"
}

Never changes for the life of the application. A machine token reads machine:51c8a0f3-… and omits the application claims.

Broken across lines for reading; it is one string. A machine token reads group:3f2a…:rank:production:machine:51c8a0f3-….

Writing a rule

The same intent, written for Anthropic (a federation rule's match block) and for AWS (an IAM role trust policy, which for a custom issuer can only test sub and aud).

Every production Tamanu central in Example Site

S1 · Anthropic 
"match": {
  "subject_prefix": "application:*",
  "claims": {
    "canopy_group_id": "3f2a9c4e-…",
    "canopy_rank": "production",
    "canopy_application_type": "tamanu-central"
  }
}
S1 · AWS 
"StringEquals": {
  "idp.canopy.bes.au:sub": [
    "application:8d41e7b2-…",
    "application:c19f04ad-…"
  ]
}

AWS cannot see the claims, so the only option is to list every central by hand and edit the policy whenever one arrives or leaves production.

S2 · Anthropic 
"match": {
  "subject_prefix":
    "group:3f2a9c4e-…:rank:production:application:tamanu-central:*"
}
S2 · AWS 
"StringLike": {
  "idp.canopy.bes.au:sub":
    "group:3f2a9c4e-…:rank:production:application:tamanu-central:*"
}

One pattern, identical on both sides. Canopy would show it ready to paste, since nobody types the group's ID.

Every production Tamanu central, any group

S1

Anthropic: drop canopy_group_id from the claims. AWS: not expressible beyond a hand-kept list of the whole fleet.

S2

AWS: group:*:rank:production:application:tamanu-central:*, since StringLike takes a wildcard anywhere. Anthropic: a prefix cannot skip the group, so use the flat claims, exactly as S1 does.

One specific application

S1

Exact sub on both sides. Keeps matching wherever the application moves.

S2

A pattern ending in the application's ID: group:*:application:*:8d41e7b2-… on AWS, canopy_application_id on Anthropic. Exact sub works too, but stops matching on a move.

Pending and ungrouped subjects

A pending machine has no rank yet; an ungrouped one has no group. Under S2 those segments have nothing to say, and under S1 the claims would be missing.

Refuse

Canopy refuses issuance until the subject has a group and a rank, and says which is missing, the way a missing DNS grant is refused. Every token then carries both, and a rule never meets a subject outside an environment.

409  This machine is pending. Give it a rank first.
Issue with a placeholder

The token carries rank:pending or group:none. A rule written as "anything in Example Site" (group:3f2a…:*) then admits a box nobody has yet placed in an environment.

"sub": "group:3f2a9c4e-…:rank:pending:application:tamanu-central:8d41…"
